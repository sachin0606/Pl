1. About this guide

Use: This manual describes how the integrated Kashtrix applications are intended to operate together. It separates operator workflow from engineering configuration. Features requiring broadcast hardware or licensed codecs must be accepted on the target system before on-air use.

Platform flow

Ingest → MAM/QC/Proxy → NRCS/MOS/Scheduler → Playout → CG → Outputs → As-Run/Traffic reconciliation

All applications share platform identity, command/event services and the common API. Operators should not have to re-enter the same media, story or graphics metadata in multiple applications.

3. Playout operator workflow

  1. Select/open the channel profile and confirm channel ID, video format and output arm state.
  2. Load or receive the rundown. Missing/invalid media should be highlighted before air.
  3. Use Preview/Cue to verify the selected media without changing Program.
  4. Use TAKE/NEXT/PLAY according to the channel automation mode. Program state must always be visible.
  5. For live events use HOLD, JIP, EXTEND or SHORTEN only when the event type supports the operation.
  6. Secondary events (CG, SCTE, caption, GPO, VDCP, RS-422, SNMP, TCP, MOS) use their event-specific parameter forms.
  7. During a commercial break, use the break editor rather than manually editing unrelated playlist fields.
  8. Monitor audio/loudness, caption/SCTE state, output status, next-event timing and alarms.
  9. As-run records are written automatically from actual on-air execution, not from planned schedule alone.
Standby node: A backup engine may decode, synchronize and monitor while transmission output remains inhibited. Do not manually arm a standby node unless the HA procedure requires it.

4. Channel Controller workflow

Each playout instance has a permanent unique channel ID. Channel Controller is not another playout engine; it orchestrates connected clients.

  1. Add the channel by ID, host/API address and optional group.
  2. Verify status: connected, active/standby, on-air item, next item, output armed, alarm count and capabilities.
  3. Open a single channel for detailed control, or select multiple channels for group operations.
  4. Group commands return individual per-channel results. One failed channel must not be hidden behind a global success message.
  5. Use maintenance mode before engineering changes to an HA node.

5. CG Controller workflow

  1. Select one or more playout targets.
  2. Select PREVIEW or PROGRAM bus. The buses remain independent.
  3. Choose a reusable CG template/composition and enter the exposed template fields.
  4. PREVIEW renders the full composition. TAKE moves the intended preview instance to Program.
  5. For multi-channel operation, the same template may use identical data or per-channel data overrides.
  6. UPDATE changes data in the existing on-air instance; it should not restart the animation unless the template defines that behavior.
  7. STOP removes a selected instance. CLEAR removes selected/all layers according to confirmation policy.

6. CG Editor workflow

New objects must start with no forced animation. Animation is an explicit authoring choice.

  • Insert Text, Shape, Line, Image, Video/Sequence, Clock, Ticker, Roll and supported HTML/Web elements.
  • Use the layer panel for Copy/Cut/Paste/Duplicate/Delete, Group/Ungroup and ordering.
  • Use the custom Kashtrix color picker with visible swatch/preview; raw hex is optional engineering detail, not the only UI.
  • Use keyframes for position, scale, rotation, opacity and supported object properties. Moving an already-keyed object updates the correct keyframe/base geometry instead of snapping back.
  • Create reusable template fields for NRCS/CG Controller data; do not hard-code journalist data inside the design.
  • Validate missing assets/fonts/data bindings before publishing a template.

7. MAM workflow

  1. Register/import media. MAM assigns a permanent asset ID.
  2. Extract technical metadata and components (video, audio languages/channels, captions/subtitles, data).
  3. Calculate/check SHA-256 and detect duplicates.
  4. Run QC. Failed assets must not silently become READY.
  5. Create proxy and thumbnails/contact-sheet as configured.
  6. Apply editorial metadata, tags, rights window and workflow state.
  7. Track versions and master/proxy relationships.
  8. Archive/restore through managed jobs with checksum verification.
  9. Playout references the MAM asset, while cache/storage services resolve the physical copy.

8. Ingest workflow

  1. Select input source and verify continuous preview/audio before recording.
  2. Choose master and optional simultaneous proxy profiles.
  3. Configure timecode policy, audio mapping, caption/subtitle capture and segment duration where supported.
  4. For scheduled ingest, set start/end or duration and recurrence. The job persists in the platform database.
  5. Low-disk and source-loss rules determine whether to stop, retry or raise alarm.
  6. On completion, recordings are automatically registered to MAM and linked master/proxy files receive the same asset context.

9. NRCS, MOS and Prompter workflow

  1. Create a rundown and ordered stories.
  2. Journalist writes story body and prompter text once.
  3. Attach MAM media and CG templates as MOS objects with their template data.
  4. Publish validates objects and sends the production rundown to Kashtrix control/Playout; configured external MOS systems receive the supported MOS transactions.
  5. Prompter reads the same story body/state and follows story order without manual copy/paste.
  6. Late story edits produce realtime updates; the control system records the revision used on air.

10. Scheduler, Traffic and As-Run

  • Scheduler creates planned events and blocks with timing modes such as Follow, Hard Start, Soft Start and Manual/Hold policies.
  • Traffic imports are normalized into Kashtrix traffic/event records. A BXF adapter is a transport/mapping boundary, not a replacement for the internal model.
  • Commercial breaks have explicit break IDs and event membership.
  • As-run comes from actual execution timestamps, actual durations and actual event/control outcomes.
  • Reconciliation compares planned vs aired and reports missing, extra, late, shortened, extended or substituted events.

11. Monitoring and HA

  • Monitor process health, decoder/render timing, storage, network I/O, output readiness, PTP/NMOS/2110 adapters, ingest jobs, MAM tasks and alarms.
  • 1+1: primary and hot backup keep synchronized rundown/event/position state; only the active output is armed.
  • N+M: shared backup capacity must be checked before accepting another failover.
  • Failover must not depend on the operator UI process.
  • All failover, maintenance and output-arm changes are audited.

13. Pre-air acceptance checklist

  • Windows solution builds all applications in Debug and Release x64.
  • Channel Controller connects to every required playout instance and shows real state.
  • CG Preview/Program and multi-channel routing are tested.
  • MAM master/proxy/checksum/QC/archive/restore are tested with production-like files.
  • Ingest scheduled master+proxy and MAM registration are tested.
  • MOS/NRCS rundown changes and Prompter updates are tested under late-edit conditions.
  • ST 2110/PTP/NMOS/2022-7 and DeckLink ANC/captions/SCTE are tested against real infrastructure.
  • HA failover is tested by process kill, machine loss, output path loss and network loss.
  • As-run/traffic reconciliation is verified against known schedules.
  • REST/WebSocket/TCP/UDP/MCP access control and audit are tested.
